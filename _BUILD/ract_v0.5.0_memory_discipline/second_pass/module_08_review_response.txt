Q1: CONFIRMED
Evidence: `src/ract/memory/probes/needle.py:134-144` (`_reduce_usable_context_window`). The reducer walks `sizes` ascending and requires `all(recall[depth].get(size, False) for depth in recall)` — i.e., every tested depth must hit at a given size for that size to count. In the scenario where depths 0.05/0.25/0.50 hit but 0.75/0.95 miss **at every size including 2000**, the very first size (2000) fails the `all()` check, the loop `break`s immediately, and `usable_context_window = 0`. The docstring at lines 28-31 calls this "conservative" and claims "a single miss at a lower depth pins the usable_context_window to the previous size", but the scenario has misses at *higher* depths (0.75/0.95) at the *smallest* size, so there is no "previous size" — the window collapses to 0. This does not distinguish a transient miss from a real boundary; a single noisy miss at depth 0.95 on the 2000-token context forces the empirical window to 0, which will drive budgets to the floor. No code path *inflates* (widens) the window, but the lack of any noise tolerance (e.g., "k-of-n depths must pass" or "require N consecutive clean sizes") means transient noise *over-narrows* aggressively.
Fix (defer to v0.6 as Flagged gap 1): Add a noise-tolerant reducer (e.g., require ≥4/5 depths per size, or require 2 consecutive clean sizes before accepting a new floor) behind a config flag; keep current reducer as default for v0.5.0 compatibility.

Q2: REFUTED
Evidence: `src/ract/memory/failure_records.py:258-275` (`aggregate`). The loop at lines 268-270 explicitly does `field_name = _FAILURE_NARROWING_MAP.get(failure_type); if field_name is None: continue`. `_FAILURE_NARROWING_MAP` (lines 203-210) contains no entry for `"contract_error"`. Therefore, even if `contract_error` dominates the counts for a function (exceeds `REPEATED_FAILURE_THRESHOLD=3`), the aggregator skips it and emits no `NarrowingProposal` for that failure type. The `counts_by_function_and_type` in the returned `AggregateReport` will reflect the high count, but `proposals` will not include a budget-narrowing entry. The adversarial concern (spurious proposal attributing data-shape issues to budget) is not realized in shipped code.

Q3: REFUTED
Evidence: `src/ract/memory/repo_fingerprint.py:247-274` (`retrieval_defaults_from_fingerprint`). The function reads **only** fields of the `fingerprint` parameter (`lsp_response_time_p95_ms`, `avg_function_tokens`, `avg_import_depth`) and compares them against hard-coded constants (250, 400.0, 10.0, 600, 60, 800, 15). No module-level cache, `random.Random`, `time.time`, `os.environ`, or other impure call appears. The docstring at line 236 explicitly states "Pure function: same fingerprint always produces the same defaults (Second Pass Q3 invariant)." The adversarial concern (hidden state drift) is not present.

Q4: PARTIAL
Evidence: `src/ract/memory/probes/scheduler.py:158-182` (`write_capability_record`). The tmp-file lifecycle: `mkstemp` → `fdopen` → `write` → `flush` → `fsync` → `os.replace(tmp_path, target)`. `os.replace` is atomic on POSIX and Windows (replaces target atomically). If the process is killed **before** `os.replace` (including between `mkstemp` and the `try` block, or during write/flush/fsync), the target file is untouched — `read_capability_record` sees the **old file intact**. If killed **during** `os.replace`, the filesystem guarantees either old or new file survives, never a truncated/corrupted target. **However**, the `except Exception` branch (lines 177-180) only runs on Python exceptions; a `SIGKILL`/process crash **does not** execute it, so the `.tmp` file **leaks on disk** (orphaned in `.rack/probes/`). This does not corrupt the capability record (target is safe), but it leaves garbage. The exception branch also swallows `FileNotFoundError` on `unlink` but would propagate other `OSError` (e.g., permission denied on cleanup), which is acceptable.
Fix (defer to v0.6 as Flagged gap 2): Register an `atexit` handler or use a context manager that attempts best-effort tmp cleanup on interpreter shutdown; alternatively, sweep orphaned `.tmp` files at next `write_capability_record` invocation.

### Orthogonal defects

1. **Needle probe reducer over-narrows on systematic deep-depth failure** (Q1 detail): The "all depths must pass" rule treats a model that consistently fails at 75%/95% depth *even at small context sizes* as having `usable_context_window=0`. This conflates "context window too small" with "model cannot retrieve from deep positions". A more useful signal would be "largest size where *at least one* depth passes" or a depth-weighted score. (Flagged gap 1 covers the noise-tolerance angle; this is a separate semantic concern.)

2. **Aggregator fallback reference value uses `input_token_count` at failure time** (`failure_records.py:253-255`): When `current_budgets` is `None`, `ref_values_by_pair` tracks the **maximum** `input_token_count` seen for each `(function, field)` in the window. A failure at `input_token_count=5000` (because the assembled context exceeded the budget) sets the reference to 5000; the proposal then narrows to `int(5000 * 0.8) = 4000`. But the *actual* budget that was in force might have been 2000 — the failure occurred *because* the input exceeded the budget. Using the failure-time input as the reference **inflates the reference upward**, producing a narrowing proposal that is *less aggressive* than warranted (or even a no-op if 4000 ≥ actual budget). This silently weakens the self-adjustment signal. The fix is to require `current_budgets` from the caller (make it non-optional) or store the *declared* budget in the `FailureRecord` at emission time (schema bump).

3. **Always-narrowing invariant can be bypassed at apply time via stale `current_budgets`**: `NarrowingProposal.__post_init__` (line 103-108) enforces `new_value <= reference_current_value` at **construction**. But `aggregate()` accepts `current_budgets: dict[tuple[str, str], int] | None` (line 228). If a caller supplies a `current_budgets` map with **stale (too-high) values**, the proposal's `reference_current_value` is inflated, `new_value = reference * 0.8` passes the invariant, yet applying that proposal to the *real* (lower) budget would **widen** it. Example: real budget = 1000; stale `current_budgets` says 2000; proposal = (ref=2000, new=1600); invariant holds (1600 ≤ 2000); apply sets budget to 1600 → **widening from 1000 to 1600**. The shipped v0.5.0 code does not include the apply verb (deferred to v0.6), but the proposal shape and invariant check are baked in. v0.6's apply step **must** re-validate `new_value <= actual_current_budget` at application time, not just at proposal construction.

4. **`failure_from_phase_record` defaults token counts to 0** (line 178-179): This makes the fallback reference in `aggregate()` (defect 2) always 0 for phase-derived failures, causing `reference <= 0` → `continue` (line 262), silently dropping those failures from narrowing consideration. Phase records should carry token counts (module_09 work), but v0.5.0 ships a bridge that discards the signal.
